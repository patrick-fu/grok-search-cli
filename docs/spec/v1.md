# Grok Search CLI V1 specification

Status: implementation-ready for private, repository-owner use at the owner's
risk. This document is normative for V1.

> [!CAUTION]
> xAI has not authorized this project to reuse Grok Build credentials or call
> the subscription proxy. The owner has accepted that risk only for private
> use. Public distribution, Homebrew publication, shared-service operation,
> and public live testing remain blocked until xAI gives this project retained
> written authorization. Technical success is not authorization.

## 1. Product boundary

V1 is a Go command-line program and a thin agent skill. It performs one Web or
X search per invocation and emits one normalized JSON result.

V1 provides:

- one `grok-search` binary for macOS and Linux;
- `web` and `x` search commands;
- read-only reuse of an existing Grok Build OAuth credential;
- stable schema-version-1 success and error JSON;
- default model `grok-4.5` plus an opaque `--model` override; and
- `skills/grok-search/SKILL.md`, which teaches an agent to invoke the binary.

V1 does not provide MCP, general chat, an OpenAI-compatible proxy, an API-key
fallback, a second OAuth flow, token refresh, streaming stdout, a configurable
provider endpoint, cache, history, telemetry, media tools, or Windows support.
The only non-search commands are help and version.

## 2. Command contract

```text
grok-search web [common flags] [web flags] [query]
grok-search x   [common flags] [x flags]   [query]
grok-search help
grok-search version
```

### 2.1 Query input

- Accept either one positional query argument or UTF-8 query bytes on stdin.
- If stdin is not a terminal, read it first. Non-empty stdin plus a positional
  query is `usage_error`; empty stdin is absent and does not disable a positional
  query. The CLI never guesses between two non-empty sources.
- With terminal stdin, exactly one positional query is required. With nonterminal
  empty stdin and no positional query, the command is also `usage_error`.
- Read at most 64 KiB. Exceeding the limit, invalid UTF-8, or a query containing
  only Unicode whitespace is `usage_error`.
- For stdin only, remove one terminal LF and its optional preceding CR. Preserve
  all other bytes. The preserved query is sent upstream and returned in the
  Search Response.
- Commands are non-interactive. They never prompt or start a login flow.

### 2.2 Common flags

| Flag | Contract |
| --- | --- |
| `--model <id>` | Default `grok-4.5`. See section 5. |
| `--auth-file <path>` | Override the default credential path for this invocation. It does not relax credential checks. |
| `--timeout <duration>` | Total deadline. Default `90s`; valid range `1s` through `180s`. |
| `--max-output-tokens <n>` | Default `1024`; valid range `128` through `4096`. |
| `--verbose` | Emit only allowlisted, sanitized, non-contractual diagnostics to stderr. |

Unknown flags, missing values, duplicate scalar flags, or out-of-range values
are `usage_error`.

### 2.3 Web flags

| Flag | Upstream field |
| --- | --- |
| repeatable `--allow-domain <domain>` | `web_search.filters.allowed_domains` |
| repeatable `--exclude-domain <domain>` | `web_search.filters.excluded_domains` |

- Allow and exclude flags are mutually exclusive.
- Accept at most five unique values, matching the current xAI
  [Responses Web Search contract](https://docs.x.ai/developers/tools/web-search).
- A domain must be an ASCII hostname of at most 253 bytes, without scheme,
  credentials, port, path, query, fragment, or wildcard. Normalize ASCII case
  to lowercase and deduplicate in first-appearance order.
- Omit `filters` when no Web filter is supplied.

### 2.4 X flags

| Flag | Upstream field |
| --- | --- |
| repeatable `--allow-handle <handle>` | `x_search.allowed_x_handles` |
| repeatable `--exclude-handle <handle>` | `x_search.excluded_x_handles` |
| `--from <YYYY-MM-DD>` | `x_search.from_date` |
| `--to <YYYY-MM-DD>` | `x_search.to_date` |

- Allow and exclude flags are mutually exclusive.
- Accept at most 20 unique handles, matching the current xAI
  [Responses X Search contract](https://docs.x.ai/developers/tools/x-search).
  A handle omits `@`, is valid UTF-8, is 1–64 bytes, and contains no whitespace
  or control character. Preserve its spelling and deduplicate by exact value in
  first-appearance order.
- Dates must be real, zero-padded Gregorian dates in the exact form
  `YYYY-MM-DD`. When both exist, `from` must not be later than `to`.
- Omit absent fields rather than sending empty arrays or strings.

The filter shapes follow xAI's documented Responses API. They have not been
independently live-validated against the subscription proxy; a provider-side
rejection is normalized as `request_rejected` and never triggers a fallback
request without the filters.

### 2.5 Output and exit status

- Search commands write exactly one compact JSON object followed by LF to
  stdout, on both expected success and expected failure.
- Diagnostics go only to stderr. `--verbose` does not change stdout.
- Help and version write human-readable text and exit successfully.

| Exit | Meaning |
| --- | --- |
| `0` | Search success, help, or version. |
| `2` | Local usage or input validation failure. |
| `3` | Credential/authentication failure. |
| `4` | Transport, provider, compatibility, response, or search failure. |
| `70` | Sanitized unexpected internal failure. |

## 3. Credential boundary

### 3.1 Location and selection

The default path is:

```text
${GROK_HOME:-$HOME/.grok}/auth.json
```

`--auth-file` overrides that complete path. There is no token environment
variable and no `GROK_AUTH_FILE` alias in V1.

Before parsing content, the credential loader must:

1. resolve the selected path to an absolute path without expanding shell
   syntax such as `~`;
2. open it read-only with a race-safe no-symlink check;
3. compare pre-open metadata with the opened file metadata;
4. require a regular file owned by the effective user;
5. reject any group or other permission bit; and
6. read at most 1 MiB.

The implementation may use `O_NOFOLLOW` where portable, or `Lstat`, open, and
`fstat`/`SameFile` checks with equivalent fail-closed behavior.

Parse the store as a map and select exactly one production xAI OAuth/OIDC
record. The record must have a non-empty `key`, `auth_mode` equal to current
`oidc` or the legacy `oauth` alias, and `oidc_issuer` exactly
`https://auth.x.ai`. Ignore API-key and non-xAI records. No eligible record is
`auth_missing`; malformed JSON, malformed credential metadata, or multiple
eligible records is `auth_invalid`. The CLI never guesses among records. This
map/value shape and the `oidc` production record were checked against the
current Grok Build schema and the local store without exposing credential data.

### 3.2 Expiry

Parse RFC 3339 `create_time` and optional `expires_at`. Treat the access
credential as expired five minutes before:

- `expires_at`, when present; otherwise
- `create_time + 30 days`, matching the observed Grok Build fallback.

Invalid timestamps, or `create_time` later than the current time plus five
minutes, are `auth_invalid`. An expired record is `auth_expired`; no network
request is made.

### 3.3 Prohibited credential behavior

V1 must never:

- refresh, rotate, revoke, log in, log out, rewrite, delete, migrate, or copy a
  credential to another store;
- inspect or use the refresh token;
- put a token or credential fragment in argv, stdout, stderr, logs, errors,
  diagnostics, crash reports, telemetry, fixtures, or persisted request data;
- send the access token to any origin other than the fixed xAI origins in this
  specification; or
- invoke Grok Build to obtain a token, discover compatibility, or repair auth.

Credential immutability is an acceptance invariant. Tests compare file bytes,
metadata, and hash before and after the operation. The production CLI does not
perform a post-request hash check because Grok Build may legitimately update
the store concurrently.

For `auth_missing`, `auth_invalid`, `auth_expired`, or `auth_rejected`, the
client-owned message tells the user to run `grok login`. The thin skill asks for
permission before an agent invokes that command. The search CLI itself never
runs it.

## 4. Provider request profile

### 4.1 Fixed network boundary

The primary credential-bearing inference request is:

```text
POST https://cli-chat-proxy.grok.com/v1/responses
```

After a qualifying model `404`, the only diagnostic request is the also
credential-bearing, credential-scoped catalog request:

```text
GET https://cli-chat-proxy.grok.com/v1/models
```

Requirements:

- use HTTPS with normal hostname and certificate verification and TLS 1.2 or
  newer;
- expose no endpoint, origin, proxy, CA, or TLS override;
- disable environment HTTP proxy routing for these credential-bearing calls;
- never follow a redirect; and
- cap connect time at the smaller of 10 seconds and the remaining total
  deadline. The model catalog gets at most 15 seconds within that same total
  deadline.

### 4.2 Headers

Explicitly set only these application headers; normal HTTP transport headers
such as `Host` and `Content-Length` are allowed:

```text
Authorization: Bearer <access token>
Accept: text/event-stream
Content-Type: application/json
x-grok-client-mode: headless
x-grok-client-identifier: grok-search-cli
x-grok-client-version: 0.2.117+grok-search-cli.<cli-version>
User-Agent: grok-search-cli/<cli-version>
```

The model-catalog request sends the same Bearer authorization, client mode,
client identifier, client version, and User-Agent; it uses
`Accept: application/json` and omits `Content-Type` because it has no body. The
same fixed-origin, TLS, environment-proxy, redirect, deadline, and redaction
rules apply to both requests. Build the compatibility value from the
compile-time floor and the binary's truthful version. A development build uses
a valid identifier such as `dev`; it never borrows the installed Grok Build
version at runtime.

Do not send `X-XAI-Token-Auth`, `x-authenticateresponse`,
`x-grok-model-override`, synthetic Grok conversation/request/session/agent IDs,
encrypted continuation state, reasoning summaries, or arbitrary user headers.

### 4.3 Body

Send this minimal Responses body, omitting empty tool filter fields:

```json
{
  "model": "grok-4.5",
  "input": "the preserved query",
  "tools": [{"type": "web_search"}],
  "tool_choice": "required",
  "stream": true,
  "store": false,
  "max_output_tokens": 1024,
  "reasoning": {"effort": "low"}
}
```

There is exactly one search tool. Do not request raw tool results, encrypted
reasoning, or continuation state.

### 4.4 Bounds and retry

- The total response body/SSE budget is 8 MiB. An individual SSE data event is
  capped at 2 MiB. The model catalog and any provider error body are capped at
  1 MiB and 64 KiB respectively.
- At most one automatic retry is permitted, after 250 ms, and only when a
  transport failure happens before any response header or body byte is
  received. Cancellation or an exhausted deadline is never retried.
- Never automatically retry an HTTP status, a partially received SSE stream,
  a provider failure event, or a normalization failure.
- A retry uses the exact query, Search Type, filters, Requested Model, headers,
  and body. It does not read or mutate credentials again.

These rules bound accidental duplicate search work. The JSON `retryable` field
describes whether a caller may choose to try later; it does not imply that this
CLI already retried.

## 5. Requested Model behavior

- Use `grok-4.5` only when `--model` is absent.
- An explicit empty value is `usage_error`.
- Treat a model ID as opaque. Require valid UTF-8, 1–256 bytes, and no Unicode
  control or whitespace characters. Do not trim, canonicalize, enumerate, or
  compare against a local allowlist.
- Send the selected ID once, as `model` in the request body. Never send a model
  header, retry with another ID, or silently fall back.
- Do not preflight `/v1/models`.
- Only after `404` from the fixed Responses route, fetch the credential-scoped
  catalog once. A valid, non-empty successful catalog that omits the exact ID
  yields non-retryable `unsupported_model`. A failed, empty, malformed, or
  ID-containing catalog leaves broad `provider_error`.
- Do not infer search capability from the model name. Provider rejection is
  `request_rejected`; completion without the requested search tool is
  `search_not_performed`.

On success, `model` remains the Requested Model. `provider_model` appears only
when one reliable completed-response model value exists and differs from it.
Provider alias resolution is disclosure, not client fallback.

## 6. Search Response

The success object is:

```json
{
  "schema_version": 1,
  "type": "web",
  "query": "Find the official xAI documentation.",
  "model": "grok-4.5",
  "provider_model": "grok-4.5-build",
  "answer": "The documentation is available at the cited URL.",
  "sources": [
    {"url": "https://docs.x.ai/", "title": "xAI Documentation"}
  ],
  "warnings": []
}
```

Rules:

- `schema_version`, `type`, `query`, `model`, `answer`, `sources`, and
  `warnings` are always present. Do not add `ok`, `status`, or `mode`.
- `type`, `query`, and `model` are request-owned.
- `provider_model` is optional under the rule in section 5.
- `sources` and `warnings` are always arrays.
- A Source is a provider-supplied citation attached to the final answer. Its
  `url` is an absolute HTTP(S) URL. Omit optional `title` when absent, a numeric
  citation marker, or exactly equal to the URL.
- Deduplicate Sources by exact URL in first citation appearance order. That
  order is not relevance rank.
- Extract citations only from supported answer annotations and completed
  response citation shapes. Never parse answer text for URLs or promote search
  tool candidate results such as `web_search_call.action.sources`.
- Never infer or expose rank, score, snippet, author, date, citation offsets,
  reasoning, tool inputs/results, headers, request IDs, raw SSE, or provider
  messages.

V1 warning codes are a closed set, ordered as shown when both apply:

1. `invalid_citations_ignored`
2. `missing_citations`

Invalid citations are ignored. No accepted citation remains a successful Search
Response with `sources: []` and `missing_citations`.

### 6.1 SSE normalization

- Parse SSE framing, including multiline `data:` fields, within the byte
  budgets. Ignore comments and unknown SSE fields. `[DONE]` carries no JSON.
- Every JSON data event must decode as an object with a non-empty event type.
- Success requires exactly one `response.completed`, terminal except for SSE
  framing/comments/`[DONE]`; completed matching search-tool evidence; and a
  non-empty answer.
- The completed response's output text is authoritative. A single
  `response.output_text.done` value is the first fallback; ordered text deltas
  are the second fallback.
- Web evidence is `response.web_search_call.completed` or a completed
  `web_search_call` output item.
- X evidence is a completed `custom_tool_call` output item whose operation name
  starts with `x_`.
- A provider failure/error event is `provider_error`; missing matching tool
  evidence is `search_not_performed`; malformed, missing, duplicate,
  non-terminal, or empty-answer completion is `invalid_provider_response`.
- A typed provider length/max-token stop is `output_truncated`, not a partial
  Search Response.

Keep this provider-shape knowledge inside the normalizer; callers consume only
the Search Response or normalized error.

## 7. Error contract

Expected failures emit:

```json
{
  "schema_version": 1,
  "error": {
    "code": "rate_limited",
    "message": "The provider rate-limited the search request.",
    "retryable": true,
    "http_status": 429,
    "retry_after_seconds": 30,
    "request_id": "safe-request-id"
  }
}
```

`message` is stable, client-owned text. Optional metadata appears only when
reliably observed:

- `http_status` is the trusted origin's exact status;
- `retry_after_seconds` accepts only an integer `Retry-After`, clamped to
  `0..3600`; and
- `request_id` is taken only from the case-insensitive `x-request-id` response
  header, limited to 128 ASCII characters in `[A-Za-z0-9._:-]`, otherwise
  omitted.

Provider bodies and mutable provider messages never enter stdout. Verbose
stderr may contain only phase, attempt count, elapsed time, HTTP status,
content type, byte counts, normalized code, sanitized request ID, and whether
tool/completion evidence was observed. It never contains query, answer,
citations, request/response body, headers, paths containing a username, or
credential material.

### 7.1 Closed V1 error codes

| Code | Evidence | Retryable | Exit |
| --- | --- | --- | --- |
| `usage_error` | Local command, flag, query, filter, or model validation | false | 2 |
| `auth_missing` | File absent or no eligible OAuth/OIDC record | false | 3 |
| `auth_unreadable` | Read/open permission or I/O failure | false | 3 |
| `auth_insecure` | Symlink, wrong owner/type/mode, race, or oversized store | false | 3 |
| `auth_invalid` | Malformed/ambiguous record or invalid timestamp | false | 3 |
| `auth_expired` | Local expiry rule | false | 3 |
| `auth_rejected` | Credential was sent and trusted origin returned `401` | false | 3 |
| `permission_denied` | `403` | false | 4 |
| `rate_limited` | `429` | true | 4 |
| `request_rejected` | `400`, `409`, or `422` | false | 4 |
| `request_too_large` | `413` | false | 4 |
| `unsupported_model` | Fixed-route `404` plus successful non-empty catalog omission | false | 4 |
| `client_incompatible` | `426` | false | 4 |
| `request_timeout` | `408` or the client-owned deadline | true | 4 |
| `transport_error` | Other network failure | true | 4 |
| `provider_unavailable` | Any `5xx` response | true | 4 |
| `provider_error` | Other non-success, provider failure event, or unknown provider case | false | 4 |
| `output_too_large` | Local SSE/body byte budget crossed | false | 4 |
| `output_truncated` | Typed provider length/max-token stop | false | 4 |
| `invalid_provider_response` | Successful-status protocol/shape invariant failed | false | 4 |
| `search_not_performed` | Completed response lacks matching completed tool evidence | false | 4 |
| `internal_error` | Sanitized unexpected local failure | false | 70 |

Do not emit `auth_revoked`, `entitlement_denied`, `not_found`, `timeout`, or
`upstream_incompatible`. Do not classify by natural-language substring. A bare
`404` is `provider_error` unless the catalog rule proves `unsupported_model`.

## 8. Internal design

Keep the product as one context and avoid a generalized multi-provider SDK.
Recommended packages are responsibilities, not mandatory public APIs:

```text
cmd/grok-search       process entry point
internal/cli          parsing, validation, JSON/exit rendering
internal/auth         race-safe read-only credential loading
internal/search       Search Type, request, response, error domain types
internal/grok         fixed request profile, transport, HTTP error mapping
internal/normalize    bounded SSE parsing and Search Response normalization
```

The application seam is conceptually:

```go
Search(ctx context.Context, request SearchRequest) (SearchResponse, *SearchError)
```

Use the standard library first. Inject `http.RoundTripper`, time, and the
read-only file opener at test boundaries. Do not expose endpoint or protocol
configuration merely to make tests possible. The transport owns HTTP and byte
budgets; the normalizer owns provider event shapes; the CLI owns only command
syntax, JSON rendering, and exit mapping.

Go 1.26 is the V1 baseline. Release builds target:

- `darwin/amd64`, `darwin/arm64`;
- `linux/amd64`, `linux/arm64`; and
- SHA-256 checksums for every archive.

CI may build and test private artifacts but must not call the live xAI proxy or
publish a public release.

## 9. Thin agent skill

`skills/grok-search/SKILL.md` must stay small and teach only:

- use `web` for current public Web information and `x` for X posts;
- prefer piping arbitrary queries through stdin;
- use filters only when the user's request requires them;
- parse the single JSON object and consume `answer`, `sources`, and `warnings`;
- treat Sources as citations, not ranked search hits;
- surface typed errors without inventing provider reasons; and
- on an authentication error, tell the user to run `grok login`; request
  explicit permission before an agent runs it.

The skill does not contain tokens, perform OAuth, call the proxy directly,
promise xAI authorization, or add MCP/general-chat behavior.

## 10. Verification and acceptance

Implementation is accepted only when all of these pass without a live provider
dependency:

1. `go test ./...`, static analysis, formatting, and four-target cross-build.
2. Table tests cover every CLI validation and every error-code/status mapping.
3. Credential tests use runtime-generated obvious test sentinels, never a
   committed credential-shaped fixture. They cover missing, unreadable,
   symlink, non-regular, wrong owner/mode, oversized, malformed, zero/multiple
   eligible records, explicit and fallback expiry, and unchanged file bytes,
   mode, metadata, and hash.
4. A fake `RoundTripper` proves exact method, URL, headers, body, no redirects,
   no environment proxy, no model fallback, one-tool isolation, filter shapes,
   catalog-after-404 behavior, response limits, deadline, and retry boundaries.
5. Reuse the sanitized Web, X, missing/invalid citation, no-tool, empty-answer,
   and malformed-event fixtures from prototype commit `2257eb6`. Add synthetic
   fixtures for duplicate completion, provider failure, truncation, and
   oversized/multiline SSE.
6. Golden tests prove exact success/error JSON, optional-field omission,
   warning order, stdout/stderr separation, and exit codes.
7. Tests scan output/diagnostics for the sentinel token, Authorization header,
   refresh-token field, raw provider body, query, and answer where prohibited.
8. Skill tests or fixtures demonstrate the stdin-first invocation and the
   permission gate before `grok login`.

An owner may run a separate, explicit manual smoke test for one Web and one X
request after reviewing the risk notice. It must be off by default, absent from
CI/release automation, use benign queries, print no raw material, and verify the
credential store stayed unchanged. Passing it does not unlock distribution.

## 11. Public-release gate

Public or shared distribution is allowed only after xAI supplies auditable
project-specific authorization covering all of:

- subscription use by this third-party automated CLI;
- the approved OAuth client/flow, scopes, redirect/device flow, and refresh
  rules;
- whether Grok Build's credential store may be read or a separate client/store
  is required;
- permitted proxy routes, models, tools, identity headers, quota, and rate
  limits;
- data retention and distribution terms; and
- an explicit exception or clarification for the AUP automated/non-human
  access restriction.

Acceptable evidence is a published xAI integration document, an applicable
contract/purchase term, or retained written xAI approval naming this project.
A successful request, public client ID, open-source license, user consent, or
owner risk acceptance is insufficient.
